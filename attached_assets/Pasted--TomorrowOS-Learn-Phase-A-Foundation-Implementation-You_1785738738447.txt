# Step 8 — Build the route-sync safeguard

Extend:

`scripts/validate-seo.mjs`

This is the most important part of Phase A.

Create a permanent validation safeguard that compares the route definitions across:

1. `src/App.tsx`
2. `src/lib/seoConfig.ts`
3. `vite.config.ts` prerender route table
4. `scripts/smoke.mjs`
5. `public/_redirects`
6. `vercel.json`

The validation should fail clearly when any of the following occurs:

## App route missing SEO configuration

A static route is registered in the application but absent from `seoConfig`.

## Indexable route missing prerender coverage

A route marked `indexable: true` is not included in the prerender table.

Prefer checking all static routes for prerender coverage if that matches the existing architecture safely.

## Prerender route missing application route

A route exists in the prerender table but is not registered in the application.

## Route missing smoke coverage

A route expected to be publicly served is not represented in smoke-test coverage.

## Route missing mirror-host configuration

A registered route is missing from either:

* `_redirects`
* `vercel.json`

Account for any deliberate exclusions already documented by the project.

## Indexable route missing indexable smoke assertion

Any route marked `indexable: true` must be present in the smoke test’s expected indexable set.

## Placeholder metadata accidentally indexable

Fail if a route marked `indexable: true` contains obvious placeholder metadata, including patterns such as:

* TBD
* Draft
* Placeholder
* Coming Soon
* Content pending
* Resource currently being prepared

This rule must not fail for the new Learn routes while they remain `indexable: false`.

## Duplicate metadata

Preserve or strengthen the existing checks for duplicate titles and descriptions.

## Clear errors

Every validation failure must identify:

* the route
* the missing or inconsistent source
* the expected correction

Do not implement a brittle solution based only on line numbers.

Use the safest parsing approach compatible with the current repository and validation style.

Do not introduce a new dependency.
